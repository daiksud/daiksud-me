皆さんは「ADR」をご存知でしょうか？

ADR は "Architecture Decision Record" の略称だとされるのが一般的です。これ以外にもいくつかの表記があるようで、"Architectural Decision Records" と書かれているケース[^1]も見られます。いずれにせよ、ADRにおいて重要なのは「**判断の記録を残す**」ということです。

[^1]: https://adr.github.io/

## ADRの重要性が増している

ADRの歴史は古く、チャッピー（ChatGPT）に聞いた感じでは、2011年にマイケル・ナイガードが書いた「[Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)」の記事を起点して紹介されることが多いようです。

そんな昔からあるADRですが、みんな「書くべきだ」「残すべきだ」とは思っている（ですよね？）ものの、いざプロジェクトが始まるとどうしても書けないことが多いのではないでしょうか。私は、プロジェクトが始まった直後は「今度こそADRをちゃんと書こう」と決意を固めてるのですが、ふと気付くと全然書いてない。結局、面倒なことや、納期に追われて忙しいなどを理由に後回しにしてしまって、そのまま結局書かずに終わります。そして後日、「なんでこんな設計にしたんだっけ？？」となります。ずっとそれを繰り返してきました（少なくとも私は）。

ところが、ClaudeやCodexなどのAIエージェントが台頭した今の時代において、ADRのような「記録」はAI登場以前よりもずっと重要な要素になっていると感じています。AIにちゃんと働いてもらうには「なんでこんな設計にしたんだっけ？」を「教える」必要があるからです（逆に、未来の自分がAIに教えてもらうためでもあります）。そして、そのADRを書くこと自体もAIに任せてサクッとやれるようになったので、以前よりADRを書くハードルがグッと下がっています。なので、「ADRをAIに書かせる」というのを実践している人も多いのではないでしょうか。

私もAIを使うようになってから、ようやくADRを書くぞという決意を守れるようになりました。守れるようになったと偉そうに言ったものの、守れるようになれた理由はもちろん、AIに書いてもらっているからです。適当に「技術的な判断が下された時は、ADRを書くこと」とでもAGENTS.mdに書いておけば、こちらが明示的に指示せずとも、AIが勝手に書いてくれます。

私は、これでもうAIに「ここはこういう事情でこうなってる」などと教えなくても、勝手に記録して、勝手に把握してくれる。そう期待していました。しばらくは。

## AIが書くADRはスロップになりがち

そんな感じで、AIにADRを勝手に書かせながら開発していたある日、ふと気になったのでADRが書き溜められているディレクトリを覗いてみました。すると仰天。作っていたものは **たいしたツールじゃないのに、ADRが大量に書かれていた** のです。その数はなんと **45個** もありました。感覚的には、自分が判断したと思っている数の5倍ぐらいありました。

なんでこんなにあるの？と思いつつ、どんなADRが書かれているのか見てみると、中には妥当かなと思うものもあります。しかし、「こんなの書く必要ある？」というようなものもいっぱいありました。例えば以下のようなADRです。

- hk + mise で pre-commit 品質ゲートを統一する
- CodeQL コードスキャンを有効化する
- Biome 2.x へ移行し vendored アセットを lint 対象外にする

などです。

チームの方針によるかな、とは思いますが、個人的にはこういう開発ツールとか開発方針に関する記録は、ADRにするほどじゃないかなぁという考えです。そんなことよりも、作っている「ツールそのものの機能」や「トレードオフ」についてだけ残っていれば良いですよね。例えば以下です。

- Bun をランタイム兼ビルドツールとして採用
- 配布形式として Single-file executable[^2] を採用

[^2]: CSSなどのアセットを内蔵して単一のバイナリファイルとして配布する機能。https://bun.com/docs/compiler/executables

など。これらは「なんでBunにしたんだろ？」とか「どういう狙いで Single-file executable にしたんだろ？」などの疑問に答えられます。こういうのは重要な記録です。

45個のADRのうち、どーでもいいもの、価値があるもの、それぞれいくつなのかざっくり数えてみました。その結果が以下です。

| ADRの種類 | 数 | 割合 |
| --- | --- | --- |
| ツールの仕様などの欲しいADR | 13 | 約29% |
| 開発方針の変遷などの要らないADR | 32 | 約71% |

なんと **おおよそ 71% が開発ツール・方針のADR** でした。こんなに必要ですかね？開発者にとって「フォーマッターはBiomeを使ってる」という情報そのものには価値があるでしょうけど、個人的にはADRにするほどではないかなと。

## ADRは増えていく一方

こんな無駄なADRが増えていくのも困りものなんですが、本当に価値のあるADRだけ残したとしても、まだ問題が残っています。

ADRについて調べると、だいたい以下のような感じで残すよ、というような紹介を見かけます。

- 名前: `ADR-0001 foo bar` のように連番を割り当てる
- 内容: (紹介記事によって多少異なるが、StatusやContext, Decisionぐらいは共通している)
  - **Status**
  - **Context**
  - **Decision**
  - Alternatives
  - Consequences

前述した大量のAIスロップADRも、このスタイルで量産されていました。

このやり方、現在主流の **Git & GitHub で管理する方針とマッチしてない** のでは？と感じる部分があります。

- 承認されていないうちから `Status: Accepted` で Pull Request を出すこと
- 判断を変えた場合に以前のADRは Superseded で残しつつ、新しいADRを増やしていく一方なこと

前者は、バージョン管理システムに入れるとか、Pull Requestで承認するとか、そういうのを想定していないルールなんだろうなと。個人的には、PR で Propose して、マージされたら Accepted でしょ？と思います。その違和感を解消するためには、Approve してもらったら Accepted に変えてからマージする、なども考えられますが、それだと（普通は）もう一度 Approve してもらう必要がある[^3]ので、面倒ですし運用としてスマートじゃないですよね。

[^3]: ブランチルールセットで `Dismiss stale pull request approvals when new commits are pushed` を有効にしている場合、PR で新しいコミットなどの変更があると Approve が無効にされる。Approve 後に改竄して承認していないものを承認したとさせないために、普通は有効にすると思う。

あとは、Superseded になって今は読まなくてもいいADRを残すのも気になります。読む必要がないなら消したら？と思ってしまいます。どうしても読みたければ過去バージョンに戻して読めば良いだけです。これも、「バージョン管理システムに入れない運用」であれば、消しちゃったら「消えちゃう」ので、そういうケースでも記録をちゃんと残すためのルールなんだろうなと推測しています。

そして、もうADRはAIに読んでほしいので、置き換え済みのADRなどは読み込んでほしくないです。要らない読み込みトークンを浪費することにもなりますし、コンテキストをムダに圧迫することにもなります。

## AI 時代の Git & GitHub に最適な ADR とは

そこで、AI が ADR を読み書きし、Git & GitHub で管理する時代において、最適な ADR の残し方を考えてみました。結論としては以下です。

- ドキュメントには、「今どうなのか (Present)」を書く
- コミットログには、「なぜそうしたのか (Why)」を書く (ADR に近い)
- コードコメントには、「なぜそうしなかったのか (Why not)」を書く
- コードには、「どうやって (How)」を書く
- テストには、「ふるまい (Behavior)」を書く

これを考える上で、大きくインスピレーションを受けたのは、t_wada さんの以下のポストです。

> コードには How\
> テストコードには What\
> コミットログには Why\
> コードコメントには Why not
>
> を書こうという話をした
>
> — [Takuto Wada (@t_wada), 2017年9月5日](https://x.com/t_wada/status/904916106153828352)

特に「**コミットログには Why**」がもっとも影響を受けました。これ以外はすべて「ファイルに書いてGitにコミットする」ものですが、コミットログだけは異なります。このコミットログを記録にうまく組み込むことが、すごく良い案だと感じました。

### ドキュメントには、「今どうなのか (Present)」を書く

ドキュメントを読む人は誰なのか？ を考えます。私は以下のように定義しました。

「**今日ジョインした人。これから開発に参加する人**」

私がもし新しいチームにジョインして開発に参加するとき、何を知りたいかというと、以下のようなことです。

- このチームの開発方針は？
- フレームワークは何か？
- DBは何を使っている？
- ディレクトリ構成は？
- コーディングルールは？

「今からコードを書くために必要な知識」です。例えば Bun を使って構築されているのなら、「Bun を使っている」ことが知りたいことです。「3ヶ月前は Node.js を使ってたんだけど、これこれこういう理由でランタイムを乗り換えることに決まって、これこれこういう比較検討を行って、結果的に Bun に乗り換えた」という情報ではありません。そんなことはどうでもいいです。

なので、ドキュメントには「今どうなのか」を書くのがベストだと考えました。

### コミットログには、「なぜそうしたのか (Why)」を書く (ADR に近い)

一方で、「なんで Bun なんか使ってるんだ？ Node.js のほうが良くない？」と思うこともあるでしょう。そう思う人は恐らく、チームにも馴染んできて、プロダクトのことをある程度理解しつつある人でしょう。そういう人が気になったときに、調べられるような手段が必要です。ドキュメントに「今」以外は書かないと決めたからといって、「なんで」というコンテキストまで削除、残さない、というのはナンセンスです。「ADR」が残りませんね。

そこで t_wada さんのアイデアを参考に「コミットログには Why」を書くことにしました。想定読者は「その変更をレビューする人」や「後からなぜその決定をしたのか知りたい人」です。コミットログは、「全員がいつも読む必要はないけど、知りたいときに引っ張り出せる場所」として丁度良いです。

また、コミットログの特徴として「時系列」も軸にあるため、「あのとき何を考えてこうしたのか？」を記録する場所としても最適です。例えば Web フレームワークを Next.js から Astro に乗り換えることにしたとして、どちらも同じ `docs/web-framework.md` というドキュメントを最新状況に更新するだけです。最初に Next.js にしたときのコミットログには、「なぜ Next.js にしたのか」が書かれているはずですし、Astro に変えたときにコミットログには「なぜ Next.js から Astro に乗り換えたのか」が、日時とともに記録されるはずです。

「そのとき何を考えたか」と「コミットログ」は相性が良いので、ADR的なものはコミットログがベストだと考えました。

### コードコメントには、「なぜそうしなかったのか (Why not)」を書く

ここからは ADR とは少しニュアンスが違いますが、「判断の記録」という意味では重要なので触れておきます。

コードを読んでいると、「なんでこんな変な実装にしてるんだ？」と思うことがしばしばあります。そういうとき、コードコメントとして「Why not」が書いてあると助かります。

Pull Request のコードレビューでも、「なんでこうしなかったんですか？」と聞くことがよくあります[^4]よね。コードコメントに最初から書いてあれば、レビュアーも負担が軽くなります。

[^4]: こう聞くと「すみません。修正しました」と直されて返ってきちゃったりして、「いや、理由を聞きたかっただけなんだが。。」となるのもしばしばあるが、それはまた別のお話。

### コードには、「どうやって (How)」を書く

これは別に意識せずとも勝手にそうなっているはずですね。「必要な機能をどうやって実現しているか」はコードそのものです。

強いて言うなら、「読みやすいコードを書くべき[^5]」だとは思います。

[^5]: [リーダブルコード](https://www.oreilly.co.jp/books/9784873115658/)

ちなみに、「AI がコードを読むんだから、別に読みにくくても問題なくない？」という疑問があるかもしれません。これに対し t_wada さんは「現時点 (2026年11月) においては、人間にとって読みやすいコードは、AI にとっても読みやすい (トークン消費が少ない) という研究結果が出ている」と、[TechLead Conference 2026 Autumn](https://eight-event.8card.net/techlead-conference/) で言ってました。

### テストには、「ふるまい (Behavior)」を書く

こちらも、AIが登場する前から変わらず、これまでのセオリー通りに書けばよいでしょう。

ただ、その「セオリー」を知らない人 (AI) もいるようで、変なテストを見かけます。以下は実際に見かけたことがあるものです。

- ABC パッケージのバージョンが `v1.2.3` か、のテスト
- 変数名が `status` になっているか、のテスト

これらは「ふるまい」のテストになっていません。恐らく、以下のような指示があったのでしょう。

- 「ABC を v1.3.0にすると不具合が出るから、v1.2.3に戻して」
- 「変数名が `stutus` で typo してるから、`status` に直して」

これらのテストは表面的なことしかテストしておらず、本質的な部分がテストできていません。「なぜそのテストをするのか」をもう少し掘り下げるべきです。例えば以下のようにします。

- 「ABC で `A` というパラメータでメソッドを呼んだら `B` という結果が返ってくるか (v1.2.3 の挙動)」[^6]
- 「`status` が `404` のときに、404 ページが表示されるか (`stutus == "404"` が常に false で不具合になっていた)」

[^6]: 厳密には、これは ABC の開発元へバグレポートを出し、ABC 側でテストすべきことです。でも、OSS へのコントリビュートを禁止されていることもあるので、直ったかどうかを簡単にテストするために有用なこともあります。

これらは、「ふるまい」をテストしています。このように、本質的なふるまいを評価するテストを書くとよいでしょう。

## 「decision-recording」スキルを作った

さて、「どこにどんなことを書くか」を決めたので、あとはその通りに書いていくだけです。もちろん、AIに書いてもらいます。

というわけで、スキルを作りました。

[**decision-recording**](https://github.com/daiksud/agents/tree/main/skills/decision-recording)

です。

ドキュメント、コミットログ、コードコメント、コード、テストについて、それぞれに書く内容を定めています。また、想定読者も定義しています。「ドキュメントを読みたい人はどんな人？」「コミットログを読みたい人はどんな人？」など、「ここに書いてあることを読みたくなるのはどんなタイミングか？」を想像して定義しました。

加えて、それらを記録しながら開発する手順と、記録を残すためのリポジトリ設定も含めました。最もチーム開発で影響が大きいのは「Pull Requestの運用」だと思います。

### PRのタイトルと本文をスカッシュマージでコミットログにする

PRはレビューを受けるという特徴があるので、それゆえに行ったり来たりしがちです。個人的には、それらの右往左往の記録までmainのコミットログに残っていても、ただのノイズなので必要ないかなと考えてます。なのでスカッシュマージします。

一方で「結果、どういう検討をして、どういう結論になったのか」は残すべきです。そのための、「マージ時のコミットメッセージはPRタイトルとPR本文」です。PRで色々議論した内容や結論を簡潔にPR本文に書いておけば、GitHubで見ても読めるし、将来的にGitHubからリポジトリを移転したとしても、コミットログに残っているのでポータビリティを確保できます。

なのでこのスキルでは **PRのタイトルと本文をそのままマージ時のコミットメッセージに使う** ことにしました。

判断した時点でPR本文やその下書きに書いておき、レビューで方針が変わったら、最終的な結論と理由を反映します。レビューコメントにだけ新しい理由があって、本文は古い説明のまま、という状態ではマージしないようにしています。

### リンク先を読まなくても分かる本文

PR本文については **リンク先が読めなくても判断理由が分かること** をルールにしました。

「詳しくはIssueを参照」だけでは、リンク先が読めなくなると何も分かりません。アクセス権が変わることもありますし、GitHub自体を使わなくなる可能性もゼロとは言えません。レビューの議論も、結論と必要な根拠は本文に取り込みます。最悪Gitさえあればなんとかなる、ということを目指しています。

でも、リンクを貼ること自体は禁止しません。元の議論や資料を詳しく調べるための補足として使います。ただし、リンク先を開くことを、判断の記録を読むための必須条件にしてはダメです。なので、レビュアーの心がけとしては「リンク先を踏まずに判断できるか」が一つのポイントとなるでしょう。

## まとめ

AIに判断の記録を書いてもらえるようになって、ADRを残すハードルは下がりました。ただ、書けるからといって増やし続けると、今必要な情報を見つけにくくなります。そこで、今から開発する人が現在の方針を把握でき、あとから「なんでこうしたんだっけ？」も調べられるように、記録する場所ごとの役割を整理しました。

| 書く場所 | 書くこと |
| --- | --- |
| ドキュメント | 今どうなのか（Present） |
| コミットログ | なぜそうしたのか（Why） |
| コードコメント | なぜそうしなかったのか（Why not） |
| コード | どうやって実現するか（How） |
| テスト | どのようにふるまうか（Behavior） |

ドキュメントは現在の方針に合わせて更新し、判断の理由はコミットログに残します。PR本文には最終的な結論と理由を書き、レビューで変わった内容も反映したうえで、タイトルと本文をスカッシュマージ時のコミットメッセージに使います。リンク先を開かなくても判断理由が分かるようにしておけば、Gitの履歴から振り返れます。

このやり方をAIにも実践してもらうために作ったのが、[decision-recording](https://github.com/daiksud/agents/tree/main/skills/decision-recording) スキルです。今必要な情報を読みやすく保ちながら、過去の判断も必要なときにたどれるようにする。そんな記録の残し方を続けていきたいと思います。
